# Security policy

## Reporting a vulnerability

Please report security problems **privately** through GitHub private vulnerability reporting:
[Report a vulnerability](https://github.com/AraviiindB/c0c0n-2026-scorecard/security/advisories/new) (Security tab → *Report a vulnerability*).
Please do not post security problems in public. We aim to acknowledge reports within 3 working days and will credit reporters who want to be named.

**In scope:** the web app at <https://araviiindb.github.io/c0c0n-2026-scorecard/> (`index.html` in this repository), the session API at <https://func-c0c0n26-8ug1oc.azurewebsites.net/api/> (source in [`api/`](api/)) and the configuration of this repository.
**Out of scope:** the Microsoft Forms, Microsoft 365/OneDrive and GitHub/GitHub Pages platforms themselves (report those to Microsoft or GitHub), volumetric denial of service, social engineering, and anything that needs an already-compromised device or browser.

## Security design

- **Calculated on the device; no accounts, no tracking.** The app is one static HTML file. Scoring and the PDF report run entirely on the participant's device. The only requests the page makes go to the workshop's session API (see [Session API](#session-api)). There are no cookies, analytics, fonts, CDNs or other third-party requests.
- **Strict Content-Security-Policy** (meta tag): `default-src 'none'`. Every script and style block is allowed only by its SHA-256 hash: there is no `'unsafe-inline'`, no `'unsafe-eval'` and no inline `style` attribute. `connect-src` allows only the session API origin (`https://func-c0c0n26-8ug1oc.azurewebsites.net`), so fetch, XHR, WebSocket, EventSource, beacon and ping requests to anywhere else are blocked, and `form-action 'none'` blocks form submissions. `img-src` allows only `data:` images. `base-uri 'none'`, `object-src 'none'`, `frame-src 'none'` and `worker-src 'none'` are also set. A CSP cannot close every channel: WebRTC, page navigation and new windows, for example, are outside it. It limits what injected code could do, but the main protection is that only the hash-pinned scripts can run, and the libraries among them are verified at build time (see below).
- **Trusted Types** (`require-trusted-types-for 'script'`) are enforced in browsers that support them. The only HTML sink is a single named policy, and every dynamic value passes through an HTML-escaping function before it reaches it. Browsers without Trusted Types still get the same escaping and the hash-only CSP.
- **Untrusted input is escaped and validated.** Everything typed by the participant, or read back from local storage, is HTML-escaped before it is shown. It is also checked against allow-lists (control codes, rating values, profile options) and length-limited. Lookup tables have no prototype, so crafted keys cannot reach built-in properties.
- **Random participant codes and device IDs.** Each participant gets a code generated with `crypto.getRandomValues` (for example `K7M-Q4X`) instead of a name or initials. Each device also gets a random 128-bit device ID, used only so that a later update replaces the earlier entry instead of adding a second one, and to count how many people are on each step. It is never shown and is not linked to the person.
- **Anti-framing and referrer protection.** A script guard keeps the page hidden inside a frame; a frame that blocks scripts shows only the static "needs JavaScript" notice. Either way, a framing site gets no usable content. The referrer policy is `no-referrer`, and the fallback Forms link also opens with `rel="noopener noreferrer"`.
- **What leaves the device.** Answers, owners and target dates are kept in the browser's local storage on the participant's device until the participant chooses *Start over*. Two kinds of request go to the session API. While the participant answers, the app sends the device ID and the number of the current step (0 to 7) each time the step changes. When the participant finishes the last scenario, it sends the participant code, the three optional profile answers, the 40 ratings, the app version and the time spent, and sends an update automatically if an answer changes later. Owners, target dates, the report and the PDF are never sent. The PDF goes only where the participant saves or shares it. The sample report (`?demo=1`) sends nothing.
- **Requests carry no credentials.** Every request is a CORS "simple" `POST` with a JSON body sent as `text/plain` and no custom headers, made with `credentials: "omit"`, `referrerPolicy: "no-referrer"`, `redirect: "error"`, `cache: "no-store"` and a timeout. There are no cookies or tokens that another site could abuse. The app never displays anything the API returns: it reads only the HTTP status and a success flag.
- **Fallback.** If the API cannot be reached after three attempts, the app keeps retrying and also offers *Open pre-filled form*. That link carries the same participant code, profile and ratings to Microsoft Forms, and they are recorded only when the participant presses *Submit* there.
- **Pinned, verified dependencies.** jsPDF 4.2.1 and jsPDF-AutoTable 5.0.8 (MIT) are embedded at fixed versions. Each build fails unless both npm tarballs match their pinned registry `sha512` integrity values and the embedded files are identical to the tarball copies apart from the trailing source-map comment, which is removed. jsPDF compiles in the npm packages fflate 0.8.1, fast-png 6.4.0, iobuffer 5.4.0 and pako 2.1.0. Their tarballs are pinned to registry `sha512` values too, and the build fails unless every source file of these packages recorded in jsPDF's source map is identical to the file in the pinned tarball. This confirms which package code jsPDF was built from; the shipped code is jsPDF's own verified file. On 7 October 2026 the GitHub Advisory Database listed no advisories for these versions except CVE-2026-45820 ([GHSA-px8p-9vwx-vf98](https://github.com/advisories/GHSA-px8p-9vwx-vf98)), a denial of service in fflate's ZIP64 reader. The app is **not affected**: that reader is not in the shipped code (the build fails if it ever appears), and the app never opens ZIP files. [`sbom.cdx.json`](sbom.cdx.json) (CycloneDX 1.6) lists every component with its hashes and dependencies, records this assessment as a VEX statement (repeated in [`osv-scanner.toml`](osv-scanner.toml) for scanners that do not read VEX), and gives the SHA-256 of `index.html`, so you can check that the file served by GitHub Pages is the one that was built (see [Verifying the page](#verifying-the-page)). Licences are in [`THIRD-PARTY-NOTICES.md`](THIRD-PARTY-NOTICES.md).
- **Repository protection.** Rulesets with no bypass, not even for administrators, protect `main` (no deletion, no force-push, linear history, signed commits only) and every tag (no deletion or moving). Every commit since the `main` ruleset was added is signed and shown as *Verified* by GitHub; the first commit predates it and is unsigned. Releases are immutable: once published, their tag and files cannot be changed. GitHub Actions is limited to GitHub-owned actions; tokens are read-only by default and cannot approve pull requests. The release workflow ([`.github/workflows/release.yml`](.github/workflows/release.yml)) runs only when started by hand on `main`, pins every action to a full commit SHA, starts with no token permissions and requests only the ones it needs. Dependabot keeps those pins up to date: version updates are proposed only after a new action version has been public for 7 days, and security updates are not delayed. Secret scanning, push protection, Dependabot alerts and private vulnerability reporting are on. The release workflow also sends the SBOM's npm components to GitHub's dependency graph, so Dependabot alerts cover the libraries embedded in `index.html`. Issues, wiki and discussions are off.

## Session API

The session API is a small Azure Functions app (Python 3.12) in its own Azure resource group. Its source is in [`api/`](api/), and it has five routes: `POST /api/v1/progress`, `POST /api/v1/submit`, `GET /api/v1/stats` (facilitators only), `GET /api/dash` (the facilitators' dashboard page) and `GET /api/health`.

- **Strict input.** A request body is at most 1 KB of strict JSON: duplicate keys, `NaN`, unknown fields and wrong types are rejected. Every field is checked against a pattern or an allow-list. The device ID must be 32 hexadecimal characters, the participant code must match the app's format, profile answers must be one of the published options, and the ratings must be exactly 40 of `Y`, `P`, `N` and `U`. Nothing a participant sends is ever turned into HTML, a formula or a query.
- **Narrow access.** Progress updates and submissions are accepted only from the two app origins, and only while the workshop session is open. Rate limits apply per device ID, per network address and overall. Only well-formed requests count towards them, so malformed requests sent from the venue's shared network address cannot use up the room's allowance. CORS allows only those two origins and never credentials. Plain HTTP is redirected to HTTPS.
- **Minimal storage.** For each device ID the API keeps the current step and the latest submission, with timestamps, in Azure Table Storage. It reaches the storage with the function's managed identity; shared-key access is disabled. It stores no IP addresses and keeps no request logs (Application Insights is not used). Network addresses are used only in memory, as a keyed hash with a random key per process, to apply the rate limits. Azure's platform may keep its own operational logs. The API and its storage are deleted after the workshop.
- **Forms copy.** The API forwards each submission to the workshop's Microsoft Form with the same fields as the pre-filled link, retrying in the background, so the backup Excel dashboard receives it too.
- **Facilitator access.** The statistics need a secret facilitator key, compared by SHA-256 in constant time, and failed attempts are rate-limited separately. The dashboard takes the key from the URL fragment, which browsers do not send to servers, keeps it only in that browser tab and removes it from the address bar. The dashboard page has its own strict CSP: hash-pinned script and style, `connect-src 'self'`, `frame-ancestors 'none'` and Trusted Types.
- **Safe responses.** Responses are JSON with `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, HSTS, `Cross-Origin-Resource-Policy: same-origin` and a `default-src 'none'` CSP. Errors never include details.
- **Pinned dependencies.** The runtime dependencies (azure-functions, Werkzeug and MarkupSafe) are pinned by version and SHA-256 in [`api/src/requirements.txt`](api/src/requirements.txt) and packaged with the code, so nothing is downloaded when the app starts.

## Verifying the page

From v1.1.1, each version of the page is published as an immutable [GitHub release](https://github.com/AraviiindB/c0c0n-2026-scorecard/releases). Before anything is signed, the release workflow checks that `index.html` matches the SHA-256 recorded in `sbom.cdx.json` and is the file GitHub Pages is serving. It then creates Sigstore-signed build-provenance and SBOM attestations for `index.html`, and GitHub adds its own signed release attestation. To check the page you were served, use a recent [GitHub CLI](https://cli.github.com/):

    curl -fsSL -o index.html https://araviiindb.github.io/c0c0n-2026-scorecard/
    gh release verify-asset index.html -R AraviiindB/c0c0n-2026-scorecard
    gh attestation verify index.html -R AraviiindB/c0c0n-2026-scorecard --signer-workflow AraviiindB/c0c0n-2026-scorecard/.github/workflows/release.yml

Without the GitHub CLI, compare the SHA-256 of the downloaded file (`sha256sum index.html`, or `Get-FileHash index.html` in PowerShell) with `SHA256SUMS.txt` in the latest release.

The page is built on the maintainer's machine and then committed to this repository. The attestations therefore prove that this repository's release workflow published this exact file; they do not prove how it was built. The build checks are described under *Pinned, verified dependencies* above.

## Room dashboard

The scores and the PDF that participants see are calculated on their own devices, so other people cannot change them. The facilitators' room dashboard shows self-reported, combined results. It is a discussion aid, not a measurement.

Submissions are anonymous, so the API cannot prove that a submission came from someone in the room: anyone who copies the request format can add made-up answers, within the rate limits and only while the session is open. The dashboard shows how many devices have submitted, so the facilitators can compare that with the room. It counts only the latest submission for each device ID. Device IDs are random and never shown, so one participant cannot replace another participant's entry. Codes starting with `TEST` are left out once real submissions arrive. Room results appear only once five participants are included, and sector averages only for groups of at least five. They show averages and the median, not the lowest or highest individual score.

The backup dashboard is an Excel workbook linked to the Microsoft Form. Microsoft Forms cannot limit who submits or check the submitted values, so anyone with the form link can add made-up answers there as well. The workbook counts only responses inside the session's response-ID window (less any IDs the facilitators exclude) and uses only the latest response for each participant code. Anyone who knows a participant's code can therefore replace that participant's entry in the workbook, so participants should keep their codes to themselves. The workbook counts and lists the codes that were answered more than once. If a later response was not sent by the code's owner, the facilitators can exclude it by its ID, and the earlier response counts again. It shows malformed codes as placeholders, scores each answer by its leading symbol (✓, ◐ or ✗) and counts anything else as *Unknown*, and reports unexpected profile values as *(not given)*. Like the API dashboard, it shows room results only once five participants are included, and averages for a sector, size or role only for groups of at least five.

## Known platform limitations

- GitHub Pages does not allow custom HTTP response headers. The protections above therefore use the meta-tag and script equivalents. `frame-ancestors` and `X-Frame-Options` cannot be set, so a script anti-framing guard is used instead.
- The page is served from the shared `araviiindb.github.io` origin. No other site is published from this account.
- The fallback pre-filled Forms link carries the ratings in its URL, so they can appear in browser history and in Microsoft's logs (or those of a network proxy that inspects HTTPS). It carries no name or email.
- The API forwards submissions to Microsoft Forms through the same web endpoint the form's own page uses, which Microsoft does not document as an API. If that stops working, submissions still reach the API dashboard, and participants can still use the pre-filled link.
